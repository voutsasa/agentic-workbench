# Agentic-workbench

Enables engineers to set up their workstation and work in an agent-enabled environment: AI coding assistants configured consistently, on a toolchain that is known to work.

## Repo structure

What each file and folder is: [`README.md`](README.md) — § *Layout*, then the role tables under it. This file carries only the rules for working in them.

**Top-level split:** `docs/` is what the workbench reads; `workstation/` is what it runs on; `skills/` is what it does. Nothing under `workstation/` should reach a generated artefact — it describes the machines this runs on, not an architecture.

**Inside `workstation/`, the split is by lifetime:** policy, route and machine state live in different files. Before adding a fact there, apply the test in `workstation/machines/README.md` — *would this still be true on the other machine?*

## Invariants

**Instruction files**

- `AGENTS.md` is the only copy of these instructions. `CLAUDE.md` and `.agents/rules/workbench.md` each hold one line, `@AGENTS.md` — add nothing else. `CLAUDE.md` stays gitignored and is written per clone by `link_config.py --claude-md --apply`: Copilot CLI reads both files, so tracking it would load everything twice on every Copilot-only clone; a clone that uses Claude Code accepts the double load (`workstation/machines/macos-workstation.md` § *Instruction loading*).

**Register and corpus**

- `SOURCES.md` is the source of truth and is edited first when a source is added or removed. Its relative links reach only the process documents that govern it — `SOURCE_CATALOGUE.md`, this file, `skills/` and the `workstation/*/README.md` indexes — enforced by `checks.register.link_allow_globs` in the `review` skill's `checks.toml`.
- Every change to `SOURCES.md` gets a matching change to `SOURCE_CATALOGUE.md`: one sentence of ≤20 words per source, mirroring structure and entries exactly. `README.md` carries no source entries.
- `docs/landing-zone/` and every `reference.md` under `workstation/cli/` and `workstation/mcp/` are machine-written — never hand-edit them.
- `docs/guidance/`: every note declares its provenance; read `docs/guidance/README.md` before adding one.
- `DEVELOPMENT-PLAN.md`'s ✓/➕ markers say whether a source is registered, not whether its file is on disk — check the path. ➕ means write the `SOURCES.md` entry first.
- `TODO.md` holds only committed new work and unproven existing gaps, each saying what would close it. Delete an item when its evidence exists, not when it feels handled. Anything found but not fixed, or started but not completed, is recorded here in the same commit.

**Skills**

- `skills/` holds skills that name `SOURCES.md`, `docs/landing-zone/` or `workstation/`; `workstation/agent/skills/` holds global ones. The line and the per-clone `.claude/skills/` links are in `skills/README.md`. A global skill may still name a `workstation/` path when it locates the workbench clone through the machine note's `repo:` field rather than assuming it is the current repo — `setup-mcp-servers` does this (`workstation/agent/skills/setup-mcp-servers/SKILL.md`).
- `ingest-source` does register mechanics only — no routing, no conversion. `fetch-to-markdown` is global: never add a register or destination directory to it.
- `setup-agents` carries no route of its own and never writes a settings file.
- The global skill list is `link_config.py`'s `SKILLS` tuple — never a prose copy.

**Workstation**

- Read `workstation/cli/<tool>/quick_start.md` before invoking a tool you haven't used this session.
- MCP servers *authored* here are project output and do not belong in `workstation/mcp/`.
- `workstation/agent/` is shared by every machine, unmodified — nothing machine-specific goes there. Its paths are linked into `~/.claude/`, so check `git status` before editing them. If it is moved or renamed, repoint the links or every session silently loses its global instructions.
- `workstation/agent/settings.json` is merged into `~/.claude/settings.json` by hand — never linked, never overwritten by any command (`workstation/agent/README.md` § *Settings are merged, never linked*). The `workstation/agent/setup/<platform>.md` routes overwrite `~/.claude/CLAUDE.md` and leave `settings.json` alone.
- A machine-specific fact belongs only in `workstation/machines/<platform>-<id>.md`. Its tool table is generated by `workstation/scripts/inventory.py`, never hand-written.
- `workstation/scripts/` stays stdlib-only, writes nothing by default, and tests with `unittest`.

**Repo mechanics**

- `.verify-claims-allow` lists only paths meant not to exist here, or per-clone/machine state not guaranteed on a fresh clone, each with a reason. A path that should exist and does not is a defect to fix, never an entry. `.verify-flags-allow` is its sibling for flag claims and stays separate for exactly that reason — it lists only a flag that *works* but that no help text documents, and a flag the tool lacks is a defect in the document. All of `.pre-push-tests`, `.pre-push-ruff`, and `.pre-push-pyright` stay repo-local: the pre-push hook is shared across repos.
- Run repository Python validation from the project `.venv`: execute the relevant `unittest` suites named in `.pre-push-tests`, then run `ruff check .`, `ruff format --check .`, and the venv interpreter with `-m pyright` (`.venv\Scripts\python.exe -m pyright` on Windows; `.venv/bin/python -m pyright` on macOS). The hook's suite list remains the source of truth; do not duplicate it in prose.

## The layer model

Sources are grouped by the architecture layer they feed, not by technology: business domain, solution architecture, data architecture, technical architecture, and implementation architecture. The first four are **inputs**; implementation architecture is the **per-project output** the workbench exists to produce.

Two cross-cutting groups sit outside the layer model deliberately — *agent working practice* governs how the agent works rather than how the system is built, and *workstation tooling* serves this repo only. Neither should leak into a generated artefact as though it were architecture.

`SOURCES.md` holds the full layer definitions, the register conventions, and the per-layer gaps still to be collected.

## The corpus is not in git

`.gitignore` excludes `docs/landing-zone/`, `workstation/cli/*/reference.md`, and `workstation/mcp/*/reference.md`. The repo tracks the register, the guides, the authored notes in `docs/guidance/`, the authored `install.md`/`quick_start.md` pairs, and the authored `setup.md` files — **not** the ingested third-party content, which is rebuildable from `SOURCES.md`.

On a fresh clone the corpus is therefore empty and every entry will look un-ingested. That is expected, not a fault. Rebuilding it is a deliberate, potentially long operation: only do a full ingestion run when explicitly asked. Otherwise assume a populated local corpus and ingest only the delta for entries whose files are genuinely missing.

## Ingestion invariant

Every `[bracket link]` entry in `SOURCES.md` should have a corresponding file at `docs/landing-zone/<bracket text>.{md,pdf}`, writing a `: ` in the title — the colon *and* the space after it — as ` - ` in the filename. If a file is missing or an entry was just added, that source hasn't been ingested yet — run it through the `ingest-source` skill (only the missing delta, not a full re-run).

**One destination exception, two trees.** Entries under *Cross-cutting aspects → 2. Workstation tooling* land beside their authored guidance instead of in `docs/landing-zone/` — under `#### CLI tools` at `workstation/cli/<bracket text>/reference.md`, and under `#### MCP servers` at `workstation/mcp/<bracket text>/reference.md`. The invariant is otherwise unchanged: still one bracket link to one ingested file, still named from the bracket text.

One exclusion: italic *see also* cross-references are not entries. Every real entry carries exactly one bracket link with an `http(s)` target, so the check stays one-to-one.

## The user installs; the agent records

Workstation tooling — CLI tools and MCP servers alike — is installed, registered, and upgraded **by the user, never by the agent**. Resolving the route, checking the package is genuine, and writing it into `install.md` or `setup.md` is the agent's work. Running `brew install`, `claude mcp add`, or an upgrade is not: it changes the user's machine, and a tool that shifts version mid-task breaks the work in progress.

Hand over the exact command and let them run it. An entry in the register means a route has been recorded, **not** that the tool is live here — verify before assuming it runs, and mark anything you could not observe as pending rather than guessing at it.

## Hard rule

For any `github.com/<owner>/<repo>` source URL, fetch the raw README directly (e.g. `raw.githubusercontent.com/<owner>/<repo>/<branch>/README.md`). Never `git clone` the repo — only the README is needed.
