Agentic Workbench · Info session

One set of rules for every AI assistant, on every machine

How the workbench organises instructions, skills, MCP servers and CLI tools so that Claude Code and GitHub Copilot behave the same way on Windows and macOS.

agentic-workbench · v0.3.0 · October 2026 · press Esc for the overview

Audience: IT management. Focus on outcomes: consistency, control, compliance, onboarding time.
Why it matters

The business outcome

Problem without it

  • Each engineer configures assistants by hand, so behaviour differs person to person
  • Tool versions drift silently and break work mid-task
  • Compliance settings (e.g. AWS Bedrock) get overwritten
  • New machines take days to become productive

What the workbench delivers

  • Consistency: one versioned instruction set, loaded by both assistants
  • Control: humans install and approve; agents only record and propose
  • Evidence: claims are backed by a command and its output
  • Faster onboarding: four documented install steps per clone

Instruction layers

Clear precedence, top to bottom

1 · RequestThe user's current request overrides everything below
2 · GlobalAGENT-INSTRUCTIONS.md: how the agent works on every machine and project (policy)
3 · ProjectAGENTS.md: repo rules and invariants; conflicts with global rules are surfaced, never silently resolved
4 · Machine~/.agentic-workbench/machine.md: measured facts about this box; wins on facts, never relaxes a rule

Claude Code reads CLAUDE.md (one line: @AGENTS.md); Copilot reads AGENTS.md directly. Same content, two entry points.

A clone is ready in four commands

# 4. Link instructions and skills ¹

workstation/agent/setup/macos.md

macOS: specific instructions

  • Compare ~/.claude/CLAUDE.md with the repo copy first; linking overwrites it
  • Link: python3 workstation/scripts/link_config.py --apply --hooks (add --agent copilot, --project)
  • Use python3; avoid modern-bash syntax (declare -A, mapfile), it fails on bash 3.2
  • BSD sed exits 0 even when nothing matched; confirm edits with git diff --stat
  • A renamed link target leaves a dangling symlink; the verify step catches it
workstation/agent/setup/windows.md

Windows: specific instructions

  • Reconcile a drifted CLAUDE.md by hand before linking; keep the union
  • Requires PowerShell 7; link with python workstation\scripts\link_config.py --apply --hooks
  • > and Out-File write UTF-16 and corrupt markdown; use Set-Content -Encoding utf8
  • The Bash tool cannot resolve PATH; drive commands through pwsh.exe
  • Ask IT for Developer Mode: live symlinks instead of copies (convenience, not a blocker)
Key principles

Eight instruction files, five rules each

Each slide below distils one markdown file the agents load or follow.

↓ to step through · Esc for the overview

workstation/agent/AGENT-INSTRUCTIONS.md · global

Global agent instructions

  • Be succinct: lead with the answer, 300-word default ceiling, tables for three or more items
  • Start small, validate, then scale: one working instance before a batch
  • Validate against the real thing: every claim closes with command, output and status
  • Code over prompt: deterministic steps become tested scripts; no model calls in gates
  • Design before build: stop and ask on effort, impact (push, delete, settings, compliance) or divergence
AGENTS.md · project

Project instructions

  • AGENTS.md is the single copy; CLAUDE.md holds only @AGENTS.md
  • SOURCES.md is the source of truth, mirrored by SOURCE_CATALOGUE.md
  • The ingested corpus is not in git; it is rebuildable from the register
  • The user installs, the agent records: no agent-run installs, upgrades or MCP registrations
  • Gaps go in TODO.md in the same commit, each saying what would close it
~/.agentic-workbench/machine.md · machine agent

The machine note

  • One fixed path on every machine, different content per machine
  • Generated by probing (inventory.py), not written by hand
  • Read before planning any command: shell, paths, tool versions, what is broken
  • A measured fact beats the policy text, but never relaxes a rule or a gate
  • Records provider binding (e.g. Bedrock on Windows) so it is never guessed
workstation/agent/README.md · agent config

Agent configuration

  • Everything in workstation/agent/ is shared by every machine, unmodified
  • settings.json is merged by hand, never linked or overwritten
  • Nothing machine-specific in the instructions: no paths, versions or shell quirks
  • Portable hooks are linked (ruff_on_edit.py); OS-specific ones are copied by hand
  • One assistant-neutral copy at ~/.agentic-workbench/AGENTS.md for future tools
workstation/machines/README.md · fact placement

Where a fact lives

  • Split by lifetime: policy, route, readiness, state
  • Test: would this still be true on the other machine? If not, it is machine state
  • Common requirements in dependencies.toml; per-machine overrides in <machine>.prerequisites.toml
  • Policy never names a platform; install.md never states an install status
  • A fact in the wrong file goes stale at the wrong rate
workstation/cli/README.md · CLI tools

CLI tools

  • Three files per tool: install, quick start, reference; load only the one you need
  • Read quick_start.md before a tool's first use in a session
  • Version behind? Report and stop; upgrading mid-task is the user's call
  • Do not cross ecosystems by name: PyPI d2 is not Terrastruct's D2
  • A platform is added only when a real machine of that platform exists
workstation/mcp/README.md · MCP servers

MCP servers

  • Only third-party servers consumed here; authored servers are project output
  • One setup.md per server: route chosen, verification, silent traps
  • Project-scope .mcp.json is tracked and shared by Claude and Copilot
  • Secrets (OAuth client IDs, PATs) stay out of the catalog
  • npx servers are unpinned: record the observed version, pin if unstable
skills/README.md · skills

Skills

  • Repo skills name this workbench's files; global skills work anywhere
  • Authored once under skills/, linked into .claude/skills/ per clone
  • Never commit that link; regenerate it per clone
  • Promoted to global only when register-free, and only on the owner's say-so
  • Deterministic steps live in tested scripts/; prose keeps only judgement
SOURCES.md · the register · ↓ for the ingestion process

What the register holds: 118 first-party sources

Grouped by the architecture layer they feed

  1. Business domain (e.g. DDD Reference)
  2. Solution architecture (viewpoints, ADRs)
  3. Data architecture
  4. Technical architecture (SDLC, experimentation, enterprise and LLM stacks)
  5. Implementation architecture: the per-project output

Cross-cutting: agent working practice; workstation tooling (CLI tools, MCP servers)

Conventions

  • First-party only: the canonical URL, never a mirror or fork
  • One entry per source; other layers get a see also
  • One entry, one file: each link resolves to one ingested file
  • Gaps listed per layer as the collection backlog

SOURCE_CATALOGUE.md mirrors the register entry for entry, with one ≤20-word line on what each source gives you.

skills/ingest-source/SKILL.md · the ingestion process

From a register entry to a local file

1 · Register

Add the entry

Edit SOURCES.md first, with its matching one-line summary in SOURCE_CATALOGUE.md in the same change

2 · Resolve

Where it lands

repo_check.py --corpus prints the destination of every entry not yet on disk; only that delta is ingested

3 · Convert

fetch-to-markdown

Routes by type (raw README, pandoc, docling, Playwright + defuddle), quality-checks pass/fail, strips base64 images

4 · Record

Confirm the catalogue

The summary line exists in the same section and position; a failed conversion is not recorded

Result: docs/landing-zone/<name>.md, gitignored and rebuildable from the register. The catalogue is written by hand alongside the register and checked for drift, not generated.

skills/ingest-source/references/workstation-tooling.md

For tools, ingestion also writes the guides

reference.md · ingested

The vendor's own documentation

Fetched by fetch-to-markdown into workstation/cli/<tool>/. Complete but long; not in git.

install.md · authored

The installation instructions

macOS and Windows commands, the version check and its expected output, runtime dependencies, install traps. The package is verified as genuine first.

quick_start.md · authored

The user guide

What the tool is for, the invocations the workbench uses, key flags, and the traps that fail silently. Checked against the installed tool's --help.

MCP servers get one authored setup.md instead: route chosen, verification, traps. The agent writes the guides; the user runs the install.

Assessment

Pros and cons: the instruction approach

Pros

  • Consistent behaviour across people, assistants and OSes
  • Versioned and reviewable like code; changes are auditable
  • Human approval gates on risky actions (push, delete, install, settings)
  • Vendor-neutral: Claude and Copilot load the same files
  • Compliance constraints recorded per machine, not lost on update

Cons

  • Prose rules are guidance: a model can still misapply them
  • Large instruction files consume context on every session
  • Windows copies go stale unless --apply is re-run
  • Requires discipline to keep facts in the right file
  • More stop-and-ask moments slow routine work
Assessment

Pros and cons: local CLI tools

Pros

  • Data stays on the workstation; no upload to third-party services
  • Deterministic, repeatable output for conversions and diagrams
  • No per-call cost; works offline once installed
  • Documented traps cut failed first attempts
  • One command reports readiness per machine

Cons

  • Each engineer installs and upgrades tools themselves
  • Versions differ between machines and can change output
  • Two OS routes to document and test for every tool
  • Corporate restrictions (admin rights, Developer Mode) limit options
  • Toolchain sprawl: 19 tools to keep current
Summary

Key takeaways

  • AI assistants are governed by versioned, reviewable policy, not individual setup
  • Humans keep control of installs, pushes and compliance settings
  • Windows and macOS share one policy; only the plumbing differs
  • Ask: Developer Mode on Windows workstations would remove the stale-copy risk
  • Ask: sponsor a periodic toolchain currency review across machines
